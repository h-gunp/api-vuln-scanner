# 백엔드 기능명세 요약

> 🔄 변경됨 (2026-07-26 재수정): JSON 계약은 수정하지 않는 정본으로 두고, 백엔드 기능을 계약의 버전·필드·생산자·소비자 관계에 맞췄다.
> 

## 1. 스캔 요청 및 상태 관리

### 파트 설명

프론트엔드의 스캔 요청을 접수하고, 전체 스캔의 현재 단계와 진행률을 관리하는 영역이다. 프론트엔드 담당자는 이 기능을 통해 스캔 시작·상태 조회·취소 기능을 구현할 수 있으며, 다른 모듈 담당자는 백엔드가 관리하는 `scan_id`를 모든 데이터의 공통 식별자로 사용해야 한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-SCAN-001` | 스캔 요청 생성 | 🔄 변경됨: 프론트엔드의 `POST /api/scans` 요청에서 `target_url`을 받아 `scan_id`를 생성한다. 실행 허용 모듈은 프론트 요청값이 아니라 백엔드가 생성하는 `target_profile.json.approved_modules`의 `authz`, `input_validation`, `data_exposure`를 기준으로 한다. |
| `BE-SCAN-002` | 대상 서버 헬스체크 | 스캐너를 실행하기 전에 대상 URL의 연결 가능 여부, 응답 상태, 타임아웃 등을 확인한다. |
| `BE-SCAN-003` | 스캔 상태 조회 | 🔄 변경됨: 프론트엔드가 `scan_id`로 `scan_status`, `report_status`, 진행률, 현재 단계와 오류 정보를 조회하도록 한다. 검사 완료와 AI·PDF 보고서 완료를 동일한 상태로 취급하지 않는다. |
| `BE-SCAN-004` | 스캔 진행 정보 제공 | 크롤링 API 수, 실행 완료 모듈 수 등 단계별 세부 진행 정보를 프론트엔드에 제공한다. |
| `BE-SCAN-005` | 실행 중인 스캔 취소 | 취소 가능한 상태의 스캔을 중단하고 관련 스캐너·LLM·실행기 작업에 취소 요청을 전달한다. |

## 2. Target Profile 생성 및 전달

### 파트 설명

백엔드가 프론트엔드의 요청과 서버 설정을 바탕으로 스캐너 입력 계약인 `target_profile.json`을 만드는 영역이다. 스캐너 담당자는 이 파일을 기준으로 대상 범위, 인증 방식, 요청 한도와 실행 가능한 모듈을 판단한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-TARGET-001` | Target Profile 생성 | 🔄 변경됨: 대상 URL, 허용 경로, 환경변수 기반 자격증명 참조, 크롤링 설정과 안전 정책을 포함한 `target_profile.json` v1.1을 생성한다. 프론트엔드에서 계정·비밀번호·토큰을 받지 않는다. |
| `BE-TARGET-002` | Target Profile 저장 | 생성된 `target_profile.json` 원본을 Artifact 저장소에 저장하고 파일 경로, 체크섬, 스키마 버전을 DB에 기록한다. |
| `BE-TARGET-003` | 스캐너 작업 요청 | `target_profile.json` 또는 해당 파일의 저장 위치를 스캐너에 전달해 인증과 API 수집 작업을 시작한다. |

## 3. 스캐너 연동 및 API 그래프 관리

### 파트 설명

스캐너가 User A/B 로그인, OpenAPI 분석, Katana 크롤링과 데이터 정규화를 수행하는 동안 백엔드가 진행 상태와 결과를 전달받는 영역이다. 백엔드는 크롤링을 직접 수행하지 않고 스캐너가 생성한 `normalized_api_graph.json`을 검증하고 저장한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-SCANNER-001` | 스캐너 진행 상태 수신 | 스캐너가 전달하는 인증, API 수집, 정규화 단계와 진행률, 수집 통계를 저장한다. |
| `BE-SCANNER-002` | 🔄 변경됨: API 그래프 전달 추적 | JSON 계약의 `스캐너 → LLM` 흐름에 따라 `normalized_api_graph.json` v1.1의 전달 상태와 Artifact 참조를 관리한다. 백엔드가 보관용 사본을 저장하더라도 JSON 내용을 추가·변경하지 않으며 별도 Runtime Context JSON을 요구하지 않는다. |
| `BE-SCANNER-003` | API 수집 요약 생성 | 정규화된 API 그래프를 이용해 전체 API 수, HTTP 메서드별 API 수와 입력 필드 수 등 프론트 표시용 통계를 계산한다. |

## 4. LLM 관계 분석 및 스캔 계획 관리

### 파트 설명

🔄 변경됨: JSON 계약상 `normalized_api_graph.json`은 스캐너가 LLM에 전달하며, `relationship_analysis.json`은 LLM이 백엔드·스캐너에, `scan_plan.json`은 LLM이 Executor에 전달한다. 백엔드는 오케스트레이션 상태와 Artifact 참조를 관리하되 계약 JSON의 필드나 상태를 임의로 바꾸지 않는다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-LLM-001` | API 관계 분석 요청 | 🔄 변경됨: 스캐너가 생성한 `normalized_api_graph.json` v1.1을 변경 없이 LLM 입력으로 연결한다. JSON 계약에 없는 `runtime_scan_context.json`이나 실제 토큰·객체 ID·원시 응답은 입력 계약에 추가하지 않는다. |
| `BE-LLM-002` | 관계 분석 결과 수신 | LLM이 생성한 `relationship_analysis.json`을 수신하고 API Operation 참조, 관계 ID, 후보 모듈과 신뢰도 값을 검증해 저장한다. |
| `BE-LLM-003` | 스캔 계획 결과 수신 | 🔄 변경됨: LLM이 `PENDING_APPROVAL`로 생성한 `scan_plan.json` v1.2의 Artifact 참조와 작업 상태를 기록한다. 정책 승인값 `authz`, `input_validation`, `data_exposure`와 계획 Module ID `BOLA-001`, `INPUT-001`, `DATA-001`을 구분해 검증한다. |
| `BE-LLM-004` | 스캔 계획 정책 검증 | 🔄 변경됨: `target_profile.json`과 `scan_plan.json.budget`을 기준으로 경로·메서드·승인 모듈·상태 변경·요청 예산을 검증한다. 현재 JSON 계약에는 승인 상태 전환 주체가 정의되어 있지 않으므로 백엔드가 `APPROVED` 또는 `REJECTED`로 바꾼다고 명시하지 않는다. |

## 5. Executor 실행 및 Verifier 결과 수신 🔄 변경됨

### 파트 설명

JSON 계약상 `scan_plan.json`은 LLM에서 Executor로 전달된다. 스캐너 구현에서는 별도 프로세스 대신 Executor 내부 검증 단계를 Verifier 역할로 사용하며, 이 역할이 `scan_result.json` v1.2를 생성한다. 즉, 계약 표의 `검증기`는 별도 서비스명이 아니라 결과 생산 역할로 해석한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-EXEC-001` | 승인 계획 실행 요청 | 🔄 변경됨: LLM에서 Executor로 전달되는 `scan_plan.json` v1.2의 실행 작업 ID를 추적한다. 계약에 없는 Runtime Context JSON 참조를 요구하지 않으며, `PENDING_APPROVAL`의 승인 주체가 확정되기 전에는 백엔드가 임의로 상태를 변경하지 않는다. |
| `BE-EXEC-002` | Executor 진행률 수신 | 현재 실행 중인 Module ID, 전체 단계 수, 완료 단계 수와 룰 판정 진행 상태를 수신해 저장한다. |
| `BE-EXEC-003` | 스캔 결과 수신 | 🔄 변경됨: Executor 내부 Verifier 역할이 생성한 `scan_result.json` v1.2를 수신하고 Finding ID, Operation 참조, 검증 규칙, 영향 필드와 Evidence 참조를 검증한다. `severity`는 이 파일에 없으므로 검사하지 않는다. |

## 6. Finding 및 Evidence 관리

### 파트 설명

🔄 변경됨: Executor 내부 Verifier 역할이 확정한 `scan_result.json` v1.2를 프론트엔드와 LLM이 소비할 수 있도록 저장·조회 형태로 제공한다. `finding_id`를 기준으로 검증 결과와 이후 생성된 AI 분석을 연결한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-FIND-001` | Finding DB 적재 | `scan_result.json`에 포함된 검증 완료 Finding을 조회용 DB 레코드로 변환하고 Evidence 참조를 연결한다. |
| `BE-FIND-002` | Finding 목록 조회 | 🔄 변경됨: 특정 스캔의 취약점 목록을 `vulnerability_type`, `query` 검색어와 페이지 조건으로 조회한다. `severity`는 `scan_result.json`에 없으므로 AI 보고서 생성 전 필터 조건으로 사용하지 않는다. |
| `BE-FIND-003` | Finding 상세 조회 | `finding_id`를 기준으로 스캔 결과와 AI 보고서 데이터를 병합해 취약점 판정 근거, 영향 필드와 대응방안을 제공한다. |
| `BE-FIND-004` | 마스킹된 Evidence 조회 | 🔄 변경됨: 백엔드가 내부 Evidence Artifact를 서비스 권한으로 조회해 토큰·비밀번호·세션·객체 식별자를 마스킹한 표시용 Evidence DTO만 제공한다. 원본 Artifact 참조나 저장 경로는 노출하지 않는다. |

## 7. AI 보고서 생성 및 다운로드

### 파트 설명

확정된 `scan_result.json`을 LLM에 전달해 취약점 원인, 공격 흐름, 영향, 대응방안과 `severity`를 생성하는 영역이다. 🔄 변경됨: `severity`는 `scan_result.json`이 아니라 `ai_report.json` v1.2에 존재한다. 백엔드는 보고서 작업 상태를 애플리케이션 상태로 별도 추적하되 JSON 계약 필드로 추가하지 않는다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-REPORT-001` | AI 보안 보고서 생성 요청 | 🔄 변경됨: 검증 완료된 `scan_result.json`과 백엔드가 마스킹한 Evidence 요약만 LLM에 전달한다. 원시 요청·응답과 실제 Artifact 저장 경로는 전달하지 않는다. |
| `BE-REPORT-002` | AI 보고서 JSON 수신 | 🔄 변경됨: `ai_report.json` v1.2를 수신해 Finding ID, Evidence 참조, LLM이 생성한 `severity`, 전체 위험도와 요약을 검증해 저장한다. 계약 설명에는 규제 매핑이 언급되지만 현재 v1.2 예시에는 필드가 없으므로 별도 매핑 필드를 요구하지 않는다. |
| `BE-REPORT-003` | AI 보고서 조회 | 프론트엔드에 전체 위험도, 보고서 요약과 Finding별 원인·공격 흐름·영향·대응방안을 제공한다. |
| `BE-REPORT-004` | PDF 보고서 생성 | AI 보고서와 대상 정보, API 수집 통계를 템플릿에 적용해 다운로드 가능한 PDF 보고서를 생성한다. |
| `BE-REPORT-005` | 보고서 파일 다운로드 | 생성이 완료된 PDF 또는 JSON 보고서의 파일 존재 여부와 접근 권한을 확인한 후 다운로드를 제공한다. |

## 8. JSON Artifact 저장 및 검증

### 파트 설명

파이프라인에서 생성되는 모든 JSON 파일과 보고서 원본을 안전하게 저장하고 관리하는 공통 영역이다. 스캐너와 LLM 담당자는 파일을 전달할 때 `scan_id`와 `schema_version`을 포함해야 하며, 백엔드는 파일 중복, 손상과 계약 위반을 검사한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-ART-001` | JSON 원본 저장 | `target_profile`, API 그래프, 관계 분석, 스캔 계획, 스캔 결과와 AI 보고서 원본을 Artifact 저장소에 보관한다. |
| `BE-ART-002` | Artifact 메타데이터 관리 | 각 파일의 유형, 스키마 버전, 저장 위치, 파일 크기, 체크섬과 생성 시각을 DB에 기록한다. |
| `BE-ART-003` | JSON 스키마 검증 | 전달받은 JSON이 해당 계약의 필수 필드, 타입과 지원하는 스키마 버전을 만족하는지 검사한다. |
| `BE-ART-004` | Artifact 무결성 검증 | SHA-256 체크섬을 계산해 파일이 전송 또는 저장 과정에서 변경되거나 손상되지 않았는지 확인한다. |
| `BE-ART-005` | 중복 콜백 멱등 처리 | 같은 `scan_id`, Artifact 유형과 체크섬을 가진 결과가 반복 전달되어도 중복 저장하거나 후속 작업을 중복 실행하지 않는다. |

## 9. 프론트엔드 데이터 제공

### 파트 설명

백엔드가 저장한 스캔 상태, API 수집 정보, 취약점 통계와 보고서를 프론트 화면에 맞는 형태로 가공하는 영역이다. 프론트엔드는 원본 JSON 구조를 직접 해석하거나 파일 간 데이터를 직접 조인하지 않고 백엔드 API의 가공된 응답을 사용한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-FE-001` | 스캔 대시보드 요약 | 🔄 변경됨: 진행률, 수집 API 수, 검사 Module 수와 Finding 수를 제공한다. 전체 위험도는 `ai_report.json` v1.2 생성 이후에만 제공하며, 보고서 작업 상태는 JSON 계약 밖의 백엔드 응답 상태로 관리한다. |
| `BE-FE-002` | 수집 API 목록 조회 | 🔄 변경됨: API Operation 목록을 HTTP 메서드, 경로와 `query` 검색어 조건으로 조회하도록 제공한다. 프론트엔드는 원본 JSON을 직접 읽지 않는다. |
| `BE-FE-003` | 취약점 통계 제공 | Finding 데이터를 취약점 유형과 심각도별로 집계해 대시보드 차트와 요약 화면에 제공한다. |

## 10. 공통 보안 및 안전 정책

### 파트 설명

외부 사용자가 내부 연동 API를 호출하거나 LLM이 허용되지 않은 공격 계획을 실행하지 못하도록 보호하는 영역이다. 모든 담당자는 실제 비밀번호, 토큰과 세션 정보를 JSON, DB 일반 컬럼 또는 로그에 포함하지 않아야 한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-SEC-001` | 내부 모듈 요청 인증 | 스캐너, LLM과 실행기가 백엔드 내부 API를 호출할 때 서비스 토큰 또는 요청 서명을 검증한다. |
| `BE-SEC-002` | 스캔 대상 Scope 검증 | 스캔 대상 URL, 경로와 HTTP 메서드가 `target_profile.json`에 정의된 허용 범위 안에 있는지 검사한다. |
| `BE-SEC-003` | 사용자 인증정보 보호 | 계정 비밀번호 대신 환경변수 참조만 사용하고 토큰, 세션과 민감정보가 파일·DB·로그에 평문 저장되지 않도록 차단한다. |
| `BE-SEC-004` | Evidence 마스킹 검증 | 프론트엔드에 제공하거나 장기 저장하는 요청·응답 증거에서 인증 헤더, 토큰과 비밀번호 등 민감정보를 제거한다. |

## 11. 외부 작업, 오류 및 재시도 관리

### 파트 설명

스캐너, LLM과 실행기가 비동기로 처리하는 작업의 시작·완료·실패를 추적하는 영역이다. 각 담당 모듈은 외부 작업 ID와 오류 코드를 백엔드에 전달해야 하며, 백엔드는 일시적 장애와 데이터 오류를 구분해 재시도 여부를 결정한다.

| 기능 ID | 기능 이름 | 기능 설명 |
| --- | --- | --- |
| `BE-JOB-001` | 외부 Job 상태 관리 | 스캐너, 관계 분석, 계획 생성, 모듈 실행과 보고서 생성 작업별 Job ID와 상태를 저장한다. |
| `BE-JOB-002` | 단계별 타임아웃 처리 | 각 외부 작업이 설정된 제한 시간을 초과하면 작업 취소를 요청하고 스캔을 `TIMED_OUT` 상태로 변경한다. |
| `BE-JOB-003` | 일시적 실패 재시도 | 네트워크 오류와 외부 서비스의 일시적 장애에 대해 제한된 횟수와 지수 백오프 방식으로 작업을 재시도한다. |
| `BE-JOB-004` | 공통 오류 형식 제공 | 프론트엔드와 내부 모듈에 오류 코드, 사용자용 메시지와 필드별 오류 내용을 동일한 JSON 구조로 제공한다. |
